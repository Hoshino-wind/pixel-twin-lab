# Componentization Workflow

Use this reference when the user wants a full image-to-component flow rather than only a pixel workbench.

## Directory Contract

Keep all intermediate artifacts under the target project:

```text
<project>/
  work/
    pixel-twin-lab/
      <run-name>/
        component-contract.json
        component-map.md
        implementation-ledger.md
        lab/
          index.html
          styles.css
          script.js
          assets/reference.png
          assets/slice-*.png
          *-capture.png
          capture-meta.json
          *-diff.png
          pixel-diff-summary.json
          regions.json
  <final-dir>/
    final component/source files written here
```

`<final-dir>` is recorded by `init_component_flow.py` but not created; create it when the first final code file is written.

Do not put screenshots, diff images, exact slices, or lab-only HTML into product source folders.

## Required Inputs

- `reference`: absolute path to the source UI image.
- `project-dir`: absolute path to the target project.
- `final-dir`: project-relative directory where final component code belongs.
- `run-name`: short slug for the workbench run.
- `framework`: actual project stack, inferred from files when possible.
- `project_profile`: generated by `init_component_flow.py`; includes package manager, framework, routing, style system, UI libraries, source roots, scripts, and defaults applied.

If `project-dir` or `final-dir` is unclear, ask before writing final product files.

## Componentization Loop

1. Initialize the run with `scripts/init_component_flow.py`.
2. Inspect the target project before writing final code. Treat this as a hard gate, not a nice-to-have:
   - package manager and scripts
   - framework and router
   - existing component/style conventions
   - asset import conventions
   - UI/component libraries already installed
   - existing chart/icon libraries
3. Read `component-contract.json` and follow `project_profile`:
   - `next-react`: follow Next App Router or Pages Router as detected.
   - `vite-react` or `react`: write React components in the project style.
   - `tailwind`: use Tailwind utilities and existing tokens/classes.
   - `css`, `css-modules`, `sass`: create styles in the project's existing pattern.
   - installed UI libraries: reuse them only when they fit the reference and local conventions.
   - `unknown`: nothing was detectable; apply the React + Tailwind default yourself per the skill's decision rules.
   - `style_system.defaulted: true` (mirrored in `defaults_applied`) means Tailwind is a fallback, not a detected convention.
4. Fill `component-map.md` with regions from the reference:
   - app shell
   - navigation/sidebar
   - top app bar
   - filters/actions
   - primary data/table area
   - detail panel
   - charts/cards/content lists
   - empty/loading/error states if needed
   Mirror these region names in a `regions.json` next to the lab captures so `pixel_diff.py` reports component-level metrics under the same vocabulary.
   For light, low-contrast, or complex dashboards where auto slice detection misses components, also write a `slice-manifest.json` with the same region names and rerun lab preparation with `--manifest` — manual slices plus auto-generated gap slices keep exact mode complete and give every named region its own diff metric.
5. Build in slices:
   - Start with page shell and layout geometry — calibrate geometry before color; a 2px layout drift turns every color comparison red.
   - Add typography and tokens; sample every color from the reference bitmap and reuse the project's existing tokens before creating new ones.
   - Add repeated components.
   - Keep maps, photos, avatars, complex charts, and logo/display text as bitmap slice islands instead of forcing them into components; the component layer owns their containers, layout, and interactions.
   - Add image assets only where source imagery cannot be represented as code.
   - Add interaction states after static geometry is stable.
6. Capture the final app route at the same viewport as the reference.
7. Run `pixel_diff.py` against the app capture or copy the app capture into the lab as `rebuilt-capture.png`. Before the first calibration pass, verify the zero baseline: the lab's `reference` capture must diff `0%` against the reference — a nonzero baseline is an environment problem (viewport, color profile, fonts, wrong server), not a CSS problem. Per-region metrics (slices + `regions.json`) tell you which component to fix next.
8. Run `plan_calibration.py` to generate the next-round repair plan: it classifies every imperfect region as a layout shift, token offset, slice-island candidate, or rebuild, and orders them into four passes (layout → visual tokens → asset islands → region rebuild loop). Follow the pass order; merge `slice-manifest.suggested.json` into the slice manifest and rerun lab preparation when island regions appear.
9. Record each iteration in `implementation-ledger.md`:
   - changed files
   - screenshot path
   - mismatch metrics (overall and worst regions)
   - remaining P0/P1/P2 issues

## Stack and Styling Rules

- Do not introduce a new styling system when the project already has one.
- Do not install Tailwind into an existing CSS Modules, Sass, styled-components, Emotion, Ant Design, MUI, Chakra, or other established codebase unless the user approves.
- Do not convert a Next project into a Vite app or a Vite app into a Next route.
- Use React + Tailwind as the default only for blank projects or projects with no detectable frontend framework and no detectable style system.
- If detection is ambiguous, inspect representative files under `src`, `app`, `pages`, and `components` before deciding.
- If the project has design tokens, theme files, or shared UI primitives, use them before creating new local tokens.

## Final Product Rules

- Write final code into the target project's own source tree, not into the lab folder.
- Follow the project's framework and style system instead of forcing the lab template into production.
- Keep only project-used assets in final source; leave reference images and slices in the intermediate run folder.
- If a perfect-pixel result uses raster slices, label it as "bitmap-perfect" and do not call it a maintainable component implementation.
- Report two metrics at handoff: `component faithful` (coded reconstruction only) and `bitmap exact` (with slice islands applied), plus the list of regions kept as islands.
- If a component implementation remains visually different, report the exact mismatch and next calibration step.

## Handoff Checklist

- Intermediate run folder exists and contains `component-contract.json`.
- Final code files are under `<project>/<final-dir>`.
- The target project builds or runs, when feasible.
- A same-viewport screenshot has been captured.
- `pixel-diff-summary.json` or equivalent metrics are attached.
- Final response links both the final files and the intermediate workbench.
